# TPM 2.0 Session Key Delivery — Three-Party PoC (TSS.CPP / TSS.MSR)

Proof-of-concept: **External** delivers a `sessionKey` to a hardware **TPM**, routing all traffic
through a **Middle** component that cannot read `sessionKey` — guaranteed by cryptography, not
by trusting Middle.

```
External  ──→  Middle  ──→  TPM
         ←──          ←──
```

Middle forwards every byte verbatim. It can see `channelKey(sessionKey)` but never has
`channelKey`, so it cannot decrypt.

---

## Terminology

| Name | Role |
|------|------|
| `sessionKey` | The payload to protect. Only External generates it; only TPM (and eventually External) may know it. |
| `SPCK-pub` / `SPCK-priv` | RSA-2048 key pair born inside the TPM. `SPCK-priv` never leaves the chip. |
| `C` | `SPCK-pub(sessionKey)` — ciphertext External gives to Middle. |
| `EK` | Endorsement Key — restricted RSA-2048 key, manufacturer-provisioned, unique per chip. Certifies AIK. |
| `AIK` | Attestation Identity Key — restricted signing key. Certifies SPCK so External can trust it. |
| `salt` | Random bytes generated by External. Sent as `SPCK-pub(salt)` — only TPM can recover it. Salt stays with External only; Middle never sees it. |
| `channelKey` | Derived by both External and TPM from `salt` via KDFa. Never transmitted. TPM uses it to re-encrypt `sessionKey` before responding. |
| `nonceCaller` | Random nonce from External, sent in StartAuthSession. |
| `nonceTPM` | Random nonce from TPM, returned in StartAuthSession response. |

---

## Flow

```
[1]  External → Middle → TPM : connect

[2]  TPM: CreatePrimary EK (derives from endorsement seed, never leaves chip)
     TPM: CreatePrimary AIK (restricted signing key)
     TPM: CreatePrimary SPCK (non-restricted decrypt key, priv never leaves chip)
     TPM: Certify(SPCK, AIK)  -- SPCK is attested by AIK, AIK by EK
     External trusts SPCK-pub via the cert chain.

[3]  External: C = SPCK-pub(sessionKey)          [local, no TPM call]
     External sends C to Middle.

[4]  External: salt = random bytes               [stays with External only]
               encryptedSalt = SPCK-pub(salt)    [local, no TPM call]
     External sends encryptedSalt to Middle.

[5]  External → Middle → TPM : StartAuthSession(encryptedSalt, nonceCaller)
     TPM:      SPCK-priv decrypts encryptedSalt -> salt (inside chip)
               generates nonceTPM
               channelKey = KDFa(salt, nonceCaller, nonceTPM)
     External: channelKey = KDFa(salt, nonceCaller, nonceTPM)  [independent, local]
     Middle:   channelKey = ???  [Middle never has salt or the KDF result]
     (nonces bind channelKey to this specific session -- prevents replay)

[6]  External → Middle → TPM : RSA_Decrypt(SPCK-priv, C)  over session
     TPM:      SPCK-priv decrypts C -> sessionKey (inside chip, never on wire)
               sends channelKey(sessionKey) over transport
     Middle:   sees channelKey(sessionKey), cannot decrypt -- no channelKey
     External: decrypts channelKey(sessionKey) with channelKey -> sessionKey

Transport sees: C, encryptedSalt, nonceCaller, nonceTPM, channelKey(sessionKey)
                -- sessionKey is never plaintext on the wire.
```

## Prerequisites

- Windows with Visual Studio 2019 or 2022 (`cl.exe` toolchain)
- Hardware TPM 2.0 chip (`Get-Tpm` → `TpmPresent: True`, `TpmReady: True`)
- Microsoft TSS.MSR (TSS.CPP) — cloned and built

**1. Clone and build TSS.CPP:**

```bat

```

Open `TSS.MSR\TSS.CPP\TSS.CPP.sln` in Visual Studio, select **Release / x64**, build the
`TSS.CPP` project. Output: `bin\x64\Release\TSS.CPP.lib` + `TSS.CPP.dll`.

**2. Clone and build this PoC:**

```bat
git clone https://github.com/tuananh-jos/tpm-vbs-poc.git
cd tpm-vbs-poc
build.bat C:\path\to\TSS.MSR\TSS.CPP
```

## Why Middle cannot read sessionKey — cryptographic argument

Middle relays raw bytes verbatim. To decrypt `channelKey(sessionKey)`, Middle would need
`channelKey`. To get `channelKey`, Middle would need `salt`. Salt is only ever transmitted
as `SPCK-pub(salt)`, and `SPCK-priv` is inside the TPM hardware — Middle cannot extract it.

This is a cryptographic guarantee, not a trust policy. Even if Middle is adversarial, it
cannot derive `channelKey` without access to TPM private key material.

---

## Implementation: MiddleDevice

`MiddleDevice` is a `TpmDevice` subclass wrapping `TpmTbsDevice`. It intercepts at the
raw byte layer (below TSS.CPP session management):

```cpp
class MiddleDevice : public TpmDevice {
    // DispatchCommand: log command code + size, forward to TpmTbsDevice
    // GetResponse:     log response size, for RSA_Decrypt extract encrypted blob
};
```

TSS.CPP owns the session object and handles parameter encryption/decryption on behalf of
External. Middle sees `channelKey(sessionKey)` in the raw response bytes but cannot decrypt
it because it has no `channelKey`.

## Security notes

### What this PoC demonstrates
`channelKey` is derived from `salt` which the transport only ever sees encrypted as
`SPCK-pub(salt)`. Middle has no path to `channelKey`, so `sessionKey` never appears plaintext
on the wire between External and TPM.

### What this PoC does NOT protect
**Memory.** After External decrypts the response, `sessionKey` is plaintext in RAM.
This PoC protects the transport only.

**Active MITM at session setup.** If transport swaps `SPCK-pub` during key delivery, it can
supply its own salt and derive `channelKey`. Fix: verify the full cert chain (EK → AIK → SPCK)
against a trusted TPM-vendor root CA before trusting `SPCK-pub`.

**TBS-level attacker.** SPCK is non-restricted — anyone with TBS access can call
`RSA_Decrypt(SPCK, encryptedSalt)` to recover `salt` directly. Using EK (restricted) as
the salt key would prevent this; EK's `restricted` attribute blocks `RSA_Decrypt` calls from
user mode. This PoC uses SPCK as salt key for simplicity.

### SHA-1 note
TSS.CPP ignores `hashAlg` in `RsaEncrypt`/`EncryptSessionSalt` and always uses SHA-1 OAEP.
All key templates must use `SHA1`. A real deployment would use SHA-256 throughout.

### Intentional omissions
- Auth values on keys are empty.
- No PCR policy binding.
- Keys are created fresh each run, not provisioned as NV keys.
- EK certificate is not validated against vendor CA.
