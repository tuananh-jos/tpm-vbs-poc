# TPM 2.0 Session Key Delivery via Salted Session — PoC (TSS.CPP / TSS.MSR)

Proof-of-concept: TPM receives an encrypted `sessionKey`, decrypts it inside the chip, then
re-encrypts it with `secret` before returning — so the transport never sees `sessionKey` in
plaintext.

---

## Terminology

| Name | Role |
|------|------|
| `sessionKey` | The payload to protect. External encrypts it to `tpm-pub`; only the TPM can open it. |
| `wrapKey` / `tpm-pub` / `tpm-priv` | RSA-2048 decrypt key born inside the TPM. `tpm-priv` never leaves the chip. |
| `EK` | Endorsement Key — restricted RSA-2048 key used only to bootstrap `secret`. |
| `salt` | Random bytes generated by external. OAEP-encrypted to EK-pub before being sent — only TPM can recover it. |
| `secret` | Ephemeral AES-128 key derived by both sides independently from `salt`. Transport never sees it. TPM uses it to re-encrypt `sessionKey` before returning. |

---

## Flow

```
1. TPM creates wrapKey (RSA-2048). tpm-priv never leaves chip. Exports tpm-pub.
2. TPM creates EK (RSA-2048, restricted). EK-priv never leaves chip. Exports EK-pub.

3. External: C = RSA-OAEP(tpm-pub, sessionKey)

4. External: generates salt (random bytes)
             encryptedSalt = RSA-OAEP(EK-pub, salt)   <- transport only sees this
             calls StartAuthSession(tpmKey=EK, encryptedSalt)
             TPM decrypts encryptedSalt with EK-priv -> salt
             both sides derive secret = KDF(salt) independently

5. External: calls RSA_Decrypt(wrapKey, C) over session
             TPM decrypts C with wrapKey-priv -> sessionKey (inside chip)
             TPM re-encrypts sessionKey with secret -> sends over transport
             TSS.CPP decrypts with secret -> external gets sessionKey

Transport sees: C, encryptedSalt, secret-encrypted(sessionKey) — no plaintext.
```

## Prerequisites

- Windows with Visual Studio 2019 or 2022 (`cl.exe` toolchain)
- Hardware TPM 2.0 chip (`Get-Tpm` → `TpmPresent: True`, `TpmReady: True`)
- Microsoft TSS.MSR (TSS.CPP) — cloned and built

---

## Build

**1. Clone and build TSS.CPP:**

```bat
git clone https://github.com/microsoft/TSS.MSR.git
```

Open `TSS.MSR\TSS.CPP\TSS.CPP.sln` in Visual Studio, select **Release / x64**, build the
`TSS.CPP` project. Output: `bin\x64\Release\TSS.CPP.lib` + `TSS.CPP.dll`.

**2. Clone and build this PoC:**

```bat
git clone https://github.com/tuananh-jos/tpm-vbs-poc.git
cd tpm-vbs-poc
build.bat C:\path\to\TSS.MSR\TSS.CPP
```

---

## Run

Run as Administrator:

```bat
tpm_poc.exe
```

Expected output:

```
recovered : "TOP-SECRET-2026!!"
correct   : yes
```

## Security notes

### What this PoC demonstrates
`secret` is derived from `salt` which the transport only ever sees OAEP-encrypted. The
transport has no path to `secret`, so it cannot decrypt the response and `sessionKey`
never appears in plaintext on the wire.

### What this PoC does NOT protect
**Memory.** After TSS.CPP decrypts the response, `sessionKey` is plaintext in the process's
RAM. This PoC protects the transport only.

**Active MITM at session setup.** If the transport swaps EK-pub during `StartAuthSession`,
it can choose its own salt, derive `secret`, and decrypt everything. Fix: verify EK certificate
chain to a trusted TPM-vendor root CA before using EK-pub as the session salt key.

### SHA-1 note
TSS.CPP ignores the `hashAlg` argument in `RsaEncrypt` and always uses SHA-1 OAEP. Key
templates use SHA-1 to match. A real deployment would use SHA-256 throughout.

### Intentional omissions
- Auth values on keys are empty.
- No PCR policy binding.
- Keys are created fresh each run, not provisioned as NV keys.
- EK certificate is not validated.
