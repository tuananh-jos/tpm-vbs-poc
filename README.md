# TPM 2.0 Session Key Delivery — Two-Process PoC

Proof-of-concept: **External** delivers a `sessionKey` to a hardware **TPM**, routing all
traffic through **Middle**. Middle cannot read `sessionKey` in plaintext from the wire —
guaranteed by TPM session encryption, not by trusting Middle.

```
external.exe ──(named pipe)──► middle.exe ──(TBS)──► TPM chip
             ◄──────────────              ◄──────────
```

---

## Key objects — what they are and what they are NOT

This is the most common source of confusion:

| Object | What it is | What it is NOT |
|--------|-----------|----------------|
| `Tpm2` | High-level API wrapper. Serializes commands, calls `TpmDevice`. Like `HttpClient` — does not know or care where bytes go. | NOT a TPM connection. NOT a TBS handle. |
| `TpmDevice` | Abstract transport interface. Decides where bytes go. | — |
| `TpmTbsDevice` | `TpmDevice` that calls Windows TBS (kernel TPM driver). Used by **Middle**. | — |
| `TpmIpcDevice` | `TpmDevice` that sends bytes over named pipe. Used by **External**. No TBS inside. | NOT a TBS caller. |
| `TBS` | Windows kernel driver that talks to the physical TPM chip. Only **Middle** has this. | — |

When External calls `tpm[session].RSA_Decrypt(...)`:
```
Tpm2.RSA_Decrypt()
  → serialize to bytes
  → TpmIpcDevice.DispatchCommand(bytes)
      → WriteFile(named_pipe, bytes)   ← pipe to Middle, NOT TBS
      → ReadFile(named_pipe, response) ← pipe from Middle
  → TSS.CPP decrypts session-encrypted response
  → returns plaintext sessionKey
```

External never calls TBS. TBS lives only in `middle.exe`.

## Terminology

| Name | Role |
|------|------|
| `sessionKey` | Payload to protect. External generates it; only External and TPM may know it in plaintext. |
| `SPCK-pub / SPCK-priv` | RSA-2048 key pair born inside TPM. `SPCK-priv` never leaves the chip. |
| `C` | `SPCK-pub(sessionKey)` — ciphertext External sends through Middle to TPM. |
| `salt` | Random bytes generated by External. Sent as `SPCK-pub(salt)` — only TPM can unwrap it. Stays in External's process memory only. |
| `channelKey` | Derived by both External and TPM from `salt` via KDFa. Never transmitted. TPM uses it to re-encrypt `sessionKey` before responding. |
| `nonceCaller` | Random nonce from External, sent in StartAuthSession. |
| `nonceTPM` | Random nonce from TPM, returned in StartAuthSession response. |

## Flow

```
[1]  external.exe starts, connects to middle.exe via named pipe.
     middle.exe owns TBS — external.exe has no TBS access.

[2]  EK → AIK → SPCK cert chain created inside TPM.
     All commands flow: External → pipe → Middle → TBS → TPM.
     External receives SPCK-pub (to encrypt payloads).

[3]  External (local, no TPM):
       C = SPCK-pub(sessionKey)

[4]  External (local, no TPM):
       salt = random bytes              [stays in external.exe memory only]
       encryptedSalt = SPCK-pub(salt)

[5]  External → pipe → Middle → TBS → TPM: StartAuthSession(encryptedSalt, nonceCaller)
     TPM: SPCK-priv decrypts encryptedSalt → salt (inside chip, never on wire)
          generates nonceTPM
          channelKey = KDFa(salt, nonceCaller, nonceTPM)
     External: channelKey = KDFa(salt, nonceCaller, nonceTPM)  [computed locally, same result]
     Middle: channelKey = ???  [Middle never has salt]

[6]  External → pipe → Middle → TBS → TPM: RSA_Decrypt(SPCK-priv, C) over session
     TPM: decrypts C → sessionKey  (inside chip)
          encrypts: channelKey(sessionKey)
          returns channelKey(sessionKey) in response
     Middle: sees channelKey(sessionKey), cannot decrypt, forwards to External
     External: decrypts channelKey(sessionKey) with channelKey → sessionKey

Wire between Middle and TPM: C, encryptedSalt, nonceCaller, nonceTPM, channelKey(sessionKey)
Wire between External and Middle: same bytes, forwarded verbatim
sessionKey never appears in plaintext on either wire.
```

## Prerequisites

- Windows with Visual Studio 2019 or 2022 (`cl.exe` toolchain)
- Hardware TPM 2.0 chip (`Get-Tpm` → `TpmPresent: True`, `TpmReady: True`)
- Microsoft TSS.MSR (TSS.CPP) — cloned and built

## Build

```bat
git clone https://github.com/microsoft/TSS.MSR.git
```

Open `TSS.MSR\TSS.CPP\TSS.CPP.sln` in Visual Studio, select **Release / x64**, build `TSS.CPP`.

```bat
git clone https://github.com/tuananh-jos/tpm-vbs-poc.git
cd tpm-vbs-poc
build.bat C:\path\to\TSS.MSR\TSS.CPP
```

Produces: `middle.exe`, `external.exe`, `TSS.CPP.dll`

## Run

Both must run as Administrator. Start **Middle first**:

```bat
# Terminal 1
middle.exe

# Terminal 2 (after Middle prints "Waiting for External...")
external.exe
```

### middle.exe output (step [6] + CONTRAST)
```
  [Middle] -> TPM  RSA_Decrypt  (329 bytes, forwarded verbatim)
  [Middle] <- TPM  RSA_Decrypt response  (78 bytes)
  [Middle]         first output param = ab3f19c4...   <- opaque, Middle cannot read
  [Middle]         (no channelKey -> cannot interpret -> forward as-is)

  [Middle] -> TPM  RSA_Decrypt  (329 bytes, forwarded verbatim)
  [Middle] <- TPM  RSA_Decrypt response  (78 bytes)
  [Middle]         first output param = 544f502d5345435245542d323032362121  <- CONTRAST
  [Middle]         (no channelKey -> cannot interpret -> forward as-is)
```

The second hex `544f502d...` decodes to `TOP-SECRET-2026!!` — Middle could read it in plaintext.

### external.exe output (step [6] + CONTRAST)
```
[6] RSA_Decrypt  (External -> Middle -> TPM)

  [PROOF] raw bytes at External pipe boundary (BEFORE TSS.CPP ParamXcrypt):
          encrypted param = ab3f19c4...
          ^ same as Middle's log -- still encrypted here
          TSS.CPP ParamXcrypt() AES-CFB-decrypts this inside external.exe...

    [External] recovered = "TOP-SECRET-2026!!"
    correct   : yes

================================================================
[CONTRAST] Same RSA_Decrypt, session WITHOUT TPMA_SESSION::encrypt
           Middle will see PLAINTEXT in its log below:

  [CONTRAST SUMMARY]
  WITH encrypt:    Middle saw = ab3f19c4...
  WITHOUT encrypt: Middle saw = 544f502d5345435245542d323032362121
  Decoded (no enc): "TOP-SECRET-2026!!"
  ^ Middle read the sessionKey in plaintext!
  TPMA_SESSION::encrypt is the ONLY difference between these two calls.
```

## Security analysis

### What this PoC demonstrates

TPM session parameter encryption (`TPMA_SESSION::encrypt`) is an **atomic hardware operation**:
1. TPM decrypts `C` with `SPCK-priv` → `sessionKey` (inside chip, never on wire)
2. TPM immediately re-encrypts with `channelKey` → `channelKey(sessionKey)` (inside chip)
3. Response carries only `channelKey(sessionKey)`

`channelKey` is derived from `salt`, which only External has. Middle never has `salt`, so
Middle cannot derive `channelKey`, so Middle cannot decrypt `channelKey(sessionKey)`.

### Known limitation: SPCK is non-restricted

**This PoC has a real vulnerability.** SPCK is a non-restricted key. An adversarial Middle
with TBS access can:
1. Parse `encryptedSalt = SPCK-pub(salt)` from the StartAuthSession bytes
2. Call `RSA_Decrypt(SPCK, encryptedSalt)` directly via TBS → recovers `salt`
3. Compute `channelKey = KDFa(salt, nonceCaller, nonceTPM)` (nonces are visible on wire)
4. Decrypt `channelKey(sessionKey)` → reads `sessionKey`

**Fix**: use **EK** (Endorsement Key) as the salt key instead of SPCK. EK has the
`restricted` attribute enforced by TPM firmware — no caller can use RSA_Decrypt on EK for
arbitrary ciphertext, even with TBS access. Only `StartAuthSession` is permitted to use EK
for unwrapping the salt.

Note: This PoC uses SPCK to avoid a TSS.CPP bug with EK in the ENDORSEMENT hierarchy on
Windows TBS. The architectural concept is correct; the salt key should be EK in production.

### What this PoC does NOT protect

**Active MITM on key delivery.** External receives `SPCK-pub` through Middle (via pipe).
Middle could swap `SPCK-pub` with its own key. External has no out-of-band verification.
Fix: verify the full cert chain (EK cert from manufacturer CA → AIK → SPCK Certify) before
trusting `SPCK-pub`.

**Memory after decryption.** Once External decrypts, `sessionKey` is plaintext in RAM.
This PoC protects transport only.

### SHA-1 note

TSS.CPP ignores `hashAlg` in OAEP operations and always uses SHA-1. All key templates use
SHA1. A real deployment would use SHA-256.
