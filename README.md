# TPM 2.0 Session Key Delivery via Salted Session — PoC (TSS.CPP / TSS.MSR)

Proof-of-concept: TPM receives an encrypted `sessionKey`, decrypts it inside the chip using
`SPCK-priv`, then re-encrypts it with `channelKey` before returning — so the transport never sees
`sessionKey` in plaintext.

---

## Terminology

| Name | Role |
|------|------|
| `sessionKey` | The payload to protect. External encrypts it with `SPCK-pub`; only `SPCK-priv` (inside chip) can open it. |
| `SPCK-pub` / `SPCK-priv` | RSA-2048 key pair born inside the TPM. `SPCK-priv` never leaves the chip. |
| `EK` | Endorsement Key — restricted RSA-2048 key used only to hide `salt` from the transport. |
| `salt` | Random bytes generated by external. Sent as `EK-pub(salt)` — only TPM can recover it. |
| `channelKey` | Ephemeral key derived by both sides from `salt` via KDF. Never transmitted. TPM uses it to re-encrypt `sessionKey` before returning. |

---

## Flow

```
1. TPM creates key pair (SPCK-pub / SPCK-priv) inside chip. SPCK-priv never leaves.
2. TPM creates EK inside chip. EK-priv never leaves.

3. External: C = SPCK-pub(sessionKey)

4. External: generates salt, generates nonceCaller
             encryptedSalt = EK-pub(salt)      <- transport only ever sees this
             calls StartAuthSession(encryptedSalt, nonceCaller)
             TPM: EK-priv decrypts encryptedSalt -> salt
             TPM: generates nonceTPM
             both sides: channelKey = KDF(salt, nonceCaller, nonceTPM)  <- never transmitted
             (nonces bind the channelKey to this specific session -- prevents replay)

5. External: calls RSA_Decrypt(SPCK-priv, C) over session
             TPM: SPCK-priv decrypts C -> sessionKey (inside chip, never on transport)
             TPM: sends channelKey(sessionKey) over transport
             External: uses channelKey to decrypt -> sessionKey plaintext in RAM

Transport sees: C, encryptedSalt, nonceCaller, nonceTPM, channelKey(sessionKey) -- no plaintext sessionKey.
```

## Prerequisites

- Windows with Visual Studio 2019 or 2022 (`cl.exe` toolchain)
- Hardware TPM 2.0 chip (`Get-Tpm` -> `TpmPresent: True`, `TpmReady: True`)
- Microsoft TSS.MSR (TSS.CPP) -- cloned and built

## Build

**1. Clone and build TSS.CPP:**

```bat
git clone https://github.com/microsoft/TSS.MSR.git
```

Open `TSS.MSR\TSS.CPP\TSS.CPP.sln` in Visual Studio, select **Release / x64**, build the
`TSS.CPP` project. Output: `bin\x64\Release\TSS.CPP.lib` + `TSS.CPP.dll`.

**2. Clone and build this PoC:**

```bat
git clone https://github.com/tuananh-jos/tpm-vbs-poc.git
cd tpm-vbs-poc
build.bat C:\path\to\TSS.MSR\TSS.CPP
```

## Security notes

### What this PoC demonstrates
`channelKey` is derived from `salt` which the transport only ever sees encrypted as `EK-pub(salt)`.
The transport has no path to `channelKey`, so `sessionKey` never appears in plaintext on the wire.

### What this PoC does NOT protect
**Memory.** After external decrypts the response, `sessionKey` is plaintext in RAM.
This PoC protects the transport only.

**Active MITM at session setup.** If the transport swaps EK-pub during `StartAuthSession`,
it can choose its own salt, derive `channelKey`, and decrypt everything. Fix: verify the EK
certificate chain to a trusted TPM-vendor root CA before using EK-pub as the salt key.

**EK usage.** This PoC uses EK directly as the salt key -- a simplification. Production
should follow the full chain: EK certifies AK (Attestation Key), AK certifies working keys.

### SHA-1 note
TSS.CPP ignores `hashAlg` in `RsaEncrypt` and always uses SHA-1 OAEP. A real deployment
would use SHA-256 throughout.

### Why two keys

`keyPair` (non-restricted) and `EK` (restricted) serve mutually exclusive roles:
- **Non-restricted**: can decrypt arbitrary external ciphertext. Required for `RSA_Decrypt(C)` where `C = SPCK-pub(sessionKey)` was created outside the TPM.
- **Restricted**: only decrypts TPM-internal format ciphertext. Required by TPM spec for the `tpmKey` parameter of `StartAuthSession`.

A single key cannot satisfy both constraints simultaneously.

### Intentional omissions
- Auth values on keys are empty.
- No PCR policy binding.
- Keys are created fresh each run, not provisioned as NV keys.
- EK certificate is not validated.
